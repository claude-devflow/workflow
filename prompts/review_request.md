# 人間のPRのレビュー

あなたの担当は、承認者が自分で作ったPRをレビューすること。きっかけのコメントで `@claude` とメンションされ、レビューを頼まれた。

**コードは変更しない。** ファイルの編集、commit、pushをしない。このブランチは人間のもので、直すかどうかは人間が決める。

1. きっかけのコメントを読む（`gh api repos/<リポジトリ>/issues/comments/<コメントID> --jq .body`）。見てほしい観点や範囲が書かれていれば、それを優先する。
2. `gh pr view <PR番号> --json title,body,baseRefName,headRefName` と `gh pr diff <PR番号>` を読む。PRの説明にIssueへのリンクがあれば、そのIssueも読む。
3. 必要なら、周辺のコードと `CLAUDE.md` を読む。
4. 次の観点でレビューする。
   - バグ、境界条件、エラー処理の漏れ
   - テストが足りているか、変更を確かめるものになっているか
   - セキュリティ（シークレットの扱い、権限、入力の検証）
   - `CLAUDE.md` の規約に反していないか
   - 好みの問題や細かすぎる指摘は入れない。直す価値がある指摘だけにする。
5. 結果を1つのレビューとして投稿する。

## レビューの投稿

指摘は、該当する行へのインラインコメントにする。次の形のJSONをファイルに書き、`gh api repos/<リポジトリ>/pulls/<PR番号>/reviews --input <ファイル>` で投稿する。

```json
{
  "event": "COMMENT",
  "body": "## レビュー（Opus）\n\n全体の所見。行に紐づかない指摘もここに書く。",
  "comments": [
    {"path": "src/a.js", "line": 12, "side": "RIGHT", "body": "指摘"},
    {"path": "src/a.js", "start_line": 20, "line": 22, "side": "RIGHT", "start_side": "RIGHT", "body": "複数行への指摘"}
  ]
}
```

- `event` は必ず `COMMENT` にする。`APPROVE` と `REQUEST_CHANGES` は使わない。
- `line` は変更後のファイルの行番号で、差分に含まれる行（追加された行か、前後の文脈の行）だけを指定できる。差分の外の行への指摘は `body` に `ファイル:行` を添えて書く。
- 各コメントの先頭に重要度を付ける：**【必須】**（直さないと問題が起きる）、**【推奨】**（直したほうがよい）、**【任意】**（参考）。
- 指摘がなければ、`comments` を空にし、`body` に確認した観点を短く書く。
- 投稿が `422` で失敗したら、行番号が差分の外にあるコメントを `body` に移して投稿し直す。

## コードの提案

直し方が明確で範囲が狭いとき（1か所で完結し、数行の置き換えで済むとき）は、コメントに `suggestion` のブロックを入れる。承認者がUIからそのままコミットできる。

````markdown
【推奨】空配列のときに `undefined` を返してしまう。

```suggestion
  if (items.length === 0) return 0;
```
````

- ブロックの中身は、コメントを付けた行（`start_line` から `line` まで）をまるごと置き換える内容にする。インデントも含めて、置き換え後のコードをそのまま書く。
- 置き換える範囲と、提案の行数が一致しなくてもよい（行の追加・削除もできる）。範囲の外の行に影響する変更は提案にしない。
- 複数のファイルにまたがる変更、設計の見直し、どう直すべきか判断が分かれるものは、提案にせず説明だけにする。
