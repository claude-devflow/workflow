# 計画

あなたの担当は、上記のIssueの計画を立てること。この工程ではコードを変更しない（ブランチの作成、commit、pushをしない）。

## 手順

1. `gh issue view <Issue番号> --comments` で、Issueの本文とやり取りをすべて読む。きっかけのコメントIDがあれば、そのコメントへの対応が今回の主題。
2. `gh pr list --state all --search "<Issue番号>"` で、このIssueのPR（`claude/issue-<Issue番号>-` で始まるブランチ）がすでにないか確認する。
3. 関係するコードと `CLAUDE.md` を読み、実装の方針を決める。
4. 次の基準で `decision` を決め、Issueに投稿する本文を `comment` に書く。

## decision の決め方

| 状況 | decision |
| --- | --- |
| すでにPRがある。または質問への回答など、返信だけで済む | `stop` |
| 要件が曖昧で、人間の判断がないと進められない | `stop`（承認者をメンションして質問する） |
| 大きすぎるので分割した（共通ルールの「Issueの分割」） | `stop` |
| 起票元が承認者で、方針が決まった | `implement` |
| 起票元がClaudeで、共通ルールの「簡単な作業」に当たる | `implement`（簡単と判断した理由を書く） |
| 起票元がClaudeで、それ以外 | `wait`（承認されたら実装する旨を書く） |
| 承認者のコメントで方針が変わり、もう一度承認が必要 | `wait` |

- 起票元がClaudeで迷ったら `wait` にする。
- 起票元が承認者のIssueで、承認者がコメントで質問に答えた場合は、内容が十分なら `implement` にする。
- 実行コンテキストの「計画のモデル」が `haiku` か `sonnet` で、コードを読んだ結果、想定より難しい（影響範囲が広い、設計の判断が要る、共通ルールの「簡単ではない作業」に当たる）とわかったときは、`escalate` にする。Opusが計画をやり直す。`comment` には理由を1文だけ書く（投稿はされない）。

## comment に書くこと

次に起動する実装担当のClaudeは、この計画のコメントを読んで作業する。それだけで実装できるように書く。

- `## 計画` の見出しで始める
- 目的と完了の条件
- 変更するファイルと、変更の方針
- テストの方針（追加・変更するテスト）
- 範囲外として切り出すもの（あれば）
- 起票元がClaudeの場合：簡単かどうかの判定と、その理由

`stop` で返信だけの場合は、見出しなしの短い返信でよい。
