# モデルの判定

あなたの担当は、上記のIssueの計画と実装に使うモデルを決めること。ツールは使わず、上記のIssueの本文とコメントだけで判断し、すぐに結果を返す。コードは読まない。

## 計画のモデル（plan_model）

| モデル | 使うとき |
| --- | --- |
| `haiku` | 誤字・文言の修正など、変更箇所がIssueに書かれていて、調べることがほとんどない |
| `sonnet` | 1〜数ファイルで完結し、方針がIssueからほぼ読み取れる |
| `opus` | 複数のモジュールにまたがる、既存の設計を読み解く必要がある、方針に選択肢がある |
| `best` | 設計の判断が中心になる、大きな機能、Issueの分割が必要になりそうなもの |

## 実装のモデル（implement_model）

| モデル | 使うとき |
| --- | --- |
| `haiku` | 機械的な変更（文言、設定値、フォーマット） |
| `sonnet` | 通常の実装 |
| `opus` | 難しいロジック、影響範囲の広い変更 |
| `best` | 計画も `best` で、難しいロジック（アルゴリズム、並行処理、複雑な状態管理など）が実装の中心になる。設定で許可されていなければ `opus` に抑えられる |

## セルフレビューのモデル（review_model）

実装のあとに、人間のレビューの前に1回だけ行うレビュー。実装のモデルより下のモデルは選ばない（選んでも実装のモデルまで引き上げられる）。

| モデル | 使うとき |
| --- | --- |
| `haiku` | 文言・コメント・設定値だけの変更で、動作が変わらない |
| `sonnet` | 小さく、影響範囲がはっきりした変更 |
| `opus` | ロジックの変更、境界条件やエラー処理が絡む変更、複数ファイルにまたがる変更 |

## 守ること

- 共通ルールの「簡単ではない作業」（DBのスキーマやマイグレーション、認証・権限、課金、デプロイやワークフロー（`.github/` 以下）の変更、外部に公開しているAPIの変更、依存パッケージのメジャー更新）に当たる可能性があれば、`plan_model` は `opus` か `best`、`implement_model` は `sonnet` 以上、`review_model` は `opus` にする。
- コメントのやり取りで方針が変わったときは、最新の内容で判断する。
- 迷ったら1段上のモデルにする。ただし、実装を `best` にするのは上の条件にはっきり当てはまるときだけにする。
- `reason` には、選んだ理由を1文で書く。
